# Context — Generator required-input budget (GH #273)

## Files and current behavior

- FACT: The generator's byte budget is declared at `src/context-envelope.ts:181`, `GENERATOR_CONTEXT_MANIFEST.inlineSizeBudgetBytes: 65_536` (siblings for other roles at `:72`, `:506`, `:569`, `:659`, `:732`, `:810`).
- FACT: Enforcement is `assertEnvelopeBudget(roleLabel, prompt, allowedByteSize, artifacts)` at `src/context-envelope.ts:1242-1256`, which compares `Buffer.byteLength(prompt, "utf-8")` against `allowedByteSize` and throws `ContextEnvelopeConfigurationError` on overflow.
- FACT: `ContextEnvelopeConfigurationError` is defined at `src/context-envelope.ts:1113-1118` with `readonly failureKind = "CONFIGURATION"` and a message prefixed `` `CONFIGURATION: ${message}` ``. It is thrown from ~15 sites in the file, including the budget check (`:1250`) and manifest validation (`:914-1103`).
- FACT: The generator envelope is assembled by `assembleGeneratorEnvelope(input: GeneratorEnvelopeInput)` at `src/context-envelope.ts:2088-2258`, which renders `prompts/generator.md` or `prompts/generator-repair.md` via `renderPrompt` (`src/prompt-template.ts`) and only ever measures the rendered prompt string with `Buffer.byteLength(text, "utf-8")` — no separate accounting for referenced-artifact bytes exists today.
- FACT: The locked contract pair (`contract.md`, the acceptance manifest) is transported "by reference" via the constant `CONTRACT_PAIR_BY_REFERENCE` at `src/context-envelope.ts:1488-1490` and wired for the generator's `contract-view` / `acceptance-manifest` artifacts at `src/context-envelope.ts:2196-2204` (paths `{{SLICE_DIR}}/contract.md`, `{{SLICE_DIR}}/{{ACCEPTANCE_MANIFEST_FILE}}`).
- FACT: By-reference artifacts are marked with a `locatorExemption` field rather than `locator` (helper `contentLocator`, `src/context-envelope.ts:875, 885-919`); today `locatorExemption` artifacts contribute **zero bytes** to the assembled-prompt byte count that `assertEnvelopeBudget` checks.
- FACT: `envelopeArtifactByteBreakdown` (`src/context-envelope.ts:1205-1240`) produces the per-artifact-class breakdown used in overflow diagnostics; it collects `locatorExemption` classes into a `byReference` name set with no byte weight attached.
- FACT: `ContextArtifactReference`-shaped artifact entries (around `src/context-envelope.ts:870-890`) carry only `artifactClass`, `artifactId`, and either `locator` or `locatorExemption` — there is no existing "required" flag or referenced-byte-weight field. (Confirms issue's ask is new plumbing, not a rename.)
- FACT: Repair-round room calculation lives inside `assembleGeneratorEnvelope`'s repair branch, `src/context-envelope.ts:2119-2166`: the stricter-only `budget` is computed, the prompt is rendered with an empty commit log (`withoutCommitLog`), `room = budget - Buffer.byteLength(withoutCommitLog, "utf-8")`, and the commit log is bounded to `room` via `boundRepairSituationCommitLog`. Because by-reference artifacts count as zero today, this room calculation does not currently reserve anything for them — this is the exact seam issue #273 says must change ("Reserve the referenced weight before calculating repair-evidence room").
- FACT: Project overrides flow through `PipelineConfig.generatorInlineSizeBudgetBytes?: number` (`src/orchestrator.ts:546`), consumed at `src/orchestrator.ts:5861-5865` and `:7968-7969`, and passed into `assembleGeneratorEnvelope` as `inlineSizeBudgetBytes`.
- FACT: Stricter-only override clamping already exists generically: `src/context-envelope.ts:1289-1294` documents "Overrides are stricter-only: the effective budget is `min(override, manifest budget)`," applied for the generator at `:2148-2151` and `:2253-2255`. Existing tests for this precedent: `src/context-envelope.test.ts:2284-2306` ("a stricter budget override still holds, and is never widened") and `:3150` ("B-10: a stricter budget override narrows the room rather than being ignored").
- FACT: The `prompt-assembly` run event is journaled at `src/orchestrator.ts:1104-1108`, immediately before every provider dispatch, inside the `withTransientRetry` callback (comment at `:1096-1102` explains this placement is deliberate so a transient re-dispatch's journal entry pairs with the immediately preceding assembly event, and the record survives even if the invocation dies before returning).
- FACT: No call site in `src/orchestrator.ts` matches `ContextEnvelopeConfigurationError` or the string `CONFIGURATION` by name (checked directly: no matches) — the thrown error propagates as a generic `Error` with `failureKind`/`CONFIGURATION`-prefixed `message`, and downstream logging (`run.log`, `run-summary.md`) formats it through whatever generic failure-recording path the orchestrator uses for a rejected/thrown invocation, not a bespoke CONFIGURATION handler. UNKNOWN: exact line(s) where a thrown `assembleGeneratorEnvelope` error is caught and turned into a run-log / run-summary entry — not located in this pass; `src/logger.ts` is the likely writer (`failureKind` appears there per grep) and should be opened before implementation.
