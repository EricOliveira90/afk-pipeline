## Data and integration

- FACT: The anchors file `.kiro/specs/afk-v2-acceptance-scope-gates/anchors/02-behavior-coverage-gate.md` (read in full) records the settled `gatePolicy.acceptance` shape as non-escalable:
  ```json
  { "acceptance": { "command": "pnpm", "args": ["exec","vitest","run","--reporter=json","--testNamePattern","{behaviorId}"], "matcher": "vitest-json" } }
  ```
  `{behaviorId}` is a literal placeholder token that must appear at least once inside `args`; a declared `acceptance` whose `args` carry no placeholder refuses the launch, naming the key. `matcher` must be the literal `"vitest-json"`; any other value refuses the launch naming the missing matcher. The derived baseline (no `gatePolicy`) uses the same shape with "the project's vitest binary" (unspecified exactly how "the project's vitest binary" is resolved — see Unknowns). Appending the behavior ID as a trailing arg, and a single `commandTemplate` string split on whitespace, are both explicitly rejected alternatives.
- FACT: Issue #85 body, D8 (`prd.md:224-238`): the matcher `vitest-json` parses `numTotalTests` from `--reporter=json` output; zero is FAIL, ≥1 all-passing is PASS; no stdout/stderr prose is parsed. "All passing" implies the matcher must also check that all matched tests passed, not just that `numTotalTests > 0` — UNKNOWN exact vitest JSON reporter field(s) for pass/fail counts (see Unknowns).
- FACT: Issue #85's "Blocked by" section names #195 (File-scope gate, `src/scope-gate.ts`, gate id `scope`) as a hard dependency specifically because "the acceptance gate's verdict is content-derived (`numTotalTests === 0` is FAIL even when vitest exits 0), but `GateResult.status` is classified from the exit code" and D22's `run` seam is what lets a gate report its own status — this slice's design must route entirely through `run`, never through `command`/`args` + the runner's own exit-code-based `classifyExecution` (`src/gate-runner.ts:874-896`), because that classifier would report PASS on an exit-0 vitest run with zero matched tests.
- FACT: Issue #85 AC list also requires: gate results "carry checkpoint tree identity and log artifacts, consistent with base-gate evidence" — already true of every `GateResult` regardless of `run` vs `command` shape (`treeId`, `logArtifactId` are populated identically for both, `src/gate-runner.ts:574-589` vs `:729-741`). "A fully green behavior set releases behavioral evaluation" mirrors `assertGateEvidenceReleasesEvaluation` (`src/post-qa-gates.ts:260`, `src/candidate-gate-phase.ts` — not opened in this pass) which already exists as a generic post-required-gates check.
- FACT: `src/gate-policy.ts`'s glob dialect (`assertGlobDialect`, `:128-148`) rejects `{`, `}`, `?`, `[`, `]`, and other metacharacters that are legal JSON/args content but meaningless to that specific matcher — the `{behaviorId}` placeholder token uses `{`/`}`, which is a literal string substitution inside `args`, unrelated to and not run through `matchesGlob`/`assertGlobDialect`. No conflict, but worth noting the two curly-brace conventions in this codebase (glob-rejected metacharacter vs. this slice's placeholder token) are unrelated mechanisms.
