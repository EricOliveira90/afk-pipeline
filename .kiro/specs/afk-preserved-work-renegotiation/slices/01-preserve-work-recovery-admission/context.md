- INFERENCE: Two slightly different "same slice number" comparisons already coexist in the codebase — `canonicalSliceNumber`'s regex-then-`String(Number(...))` normalization (`src/afk-manifest.ts:240-243`) versus `matchesSliceSelector`'s inline `Number(value) === Number(slice.number)` (`src/slice-selector.ts:14`). ## Patterns and test harness

- FACT: `RUN_STATE_VERSION = 6` at `src/run-state.ts:67`; the doc comment at `:49-66` lists each version's additive change in one running block — ADR 0018's "same version comment block" pattern referenced in this repo's CLAUDE.md. A new recovery-lineage field is additive (a new optional `RunState` member) and must extend this same comment block, not just bump the number.
- FACT: The wiring pattern for a new optional run-state field, read from three existing examples (`sanitizeApprovedBaselines` `:593-621`, `sanitizeQualityStages` `:812-908`): (1) add optional member to the `RunState` interface (`:246-339`); (2) write a `sanitizeX` function that degrades malformed/missing data to `undefined` rather than throwing; (3) wire it into `adaptLoadedState` (`:1022-1147`) — read raw field, sanitize, conditionally spread; (4) add a focused reader (e.g. `approvedBaselineFor` `:624-629`) and writer (e.g. `recordApprovedBaseline` `:636-649`) that goes through the transaction API, not direct field mutation.
- FACT: `src/run-state.ts:545-557` — `transactRunState<T>(repoRoot, prdSlug, transaction)` loads state, invokes `transaction(state) => {changed, result}`, writes only if `changed`, all inside `withRunStateLock` (`:516-522`, which delegates to `withFileLock` keyed on the state file path). `updateRunState<T>(repoRoot, prdSlug, update)` (`:559-568`) is the always-changed convenience wrapper. This is the transaction primitive admission step 5 (acquire lock, reload, recheck, append `PENDING`) must use.
- FACT: `writeRunState(path, state)` (`:524-536`) always stamps `version: RUN_STATE_VERSION` regardless of the in-memory literal's version field.
- FACT: Append-only-event precedent to model recovery lineage on: `recordQualityStageRound`/`recordQualityStageOutcome` (`src/run-state.ts:931-991`) append per-round records rather than mutating a summary field, and `PersistedQualityStageRound` (`:192-210`) is a discrete per-event record type — structurally close to what a `PENDING`/`COMPLETED`/`ROLLED_BACK`/`ROLLBACK_FAILED` lineage event list needs.
- FACT: `src/file-lock.ts:103-171` — `withFileLock<T>(targetPath, action, options?: {timeoutMs?, pollMs?, afterLockPublished?})` is the sole ADR 0056 lock export. Lock file is `${targetPath}.lock`; owner metadata (`{version:1, pid, token, acquiredAt}`) is written via a `pendingPath` + `linkSync` atomic-rename (`:132-149`), with dead-owner reaping via `reapDeadOwner` (`:80-95`) using `process.kill(pid, 0)` liveness checks (`processIsAlive` `:32-39`). Default timeout/poll: `DEFAULT_TIMEOUT_MS`/`DEFAULT_POLL_MS` (`:13-14`, 30s/20ms); times out with `` `Timed out after ${timeoutMs}ms waiting for cross-process lock ${lockPath}` `` (`:121-125`).
- FACT: `afterLockPublished` (`src/file-lock.ts:109-110`) is documented as a test seam, fired after the owner record is durably visible but before `action()` runs. `src/file-lock.test.ts` uses this hook plus sentinel files (`ready`, `release`, `entered`, `order`) to deterministically synchronize two real spawned child processes for cross-process contention testing — the required template for this slice's "cross-process contention test against the run-state lock" acceptance criterion.
- FACT: `src/file-lock.test.ts` (structure, `:1-80`) spawns real Node child processes via `spawn(process.execPath, ["--import", "tsx", "--input-type=module", "-e", script, ...args])` with inline TS source strings as `INITIALIZER_SCRIPT`/`CONTENDER_SCRIPT`; `afterEach` kills leftover children and `rmSync`s temp dirs.
- FACT: `src/run-state.test.ts` (structure, `:1-50`) is plain vitest (`describe/it/expect/afterEach`), uses `mkdtempSync(join(tmpdir(), "afk-..."))` for isolated repo roots, and calls exported functions directly against a real temp filesystem — no fs mocking.
- FACT: Issue #277 and prd.md both state this slice must not add a spawned pipeline scenario; admission is proven entirely through exported seams (flag parsing, canonical identity, fingerprint encoder, eligibility, snapshot publication, locked `PENDING` write) plus the file-lock-style cross-process contention test (issue #277 "Second, admission is therefore proven..."; prd.md "Testing Decisions").
- FACT: This repo's CLAUDE.md test-loop-discipline section requires, for an AFK-pipeline slice agent: run `pnpm test:fast` plus the heavy suites the change touches; never run the full `pnpm test` suite as a slice agent.
- INFERENCE: Because no git/worktree module may be modified (issue #277) and no spawned pipeline scenario may be added (prd.md, issue #277), none of the four biggest heavy suites (`orchestrator`, `wave`, `resume-integration`, `qa-orchestration`) are expected to be touched by this slice's own new tests — drawn from the module-boundary and test-strategy constraints above. This does not exempt running `pnpm test:fast` before handoff.
- FACT: ADR governance for this slice, per prd.md:11-14: ADR 0018 (run state versioning), ADR 0039 (never destroy unmerged commits — relevant to the "no merge/reset/rebase" and rollback-restore constraints), ADR 0050–0051 (focused revision bounds and rollback), ADR 0055 (accepted-pair validation, lock gate and provenance), ADR 0056 (run-state lock), ADR 0062 (contract revision lineage carries its delta and names its pair).
