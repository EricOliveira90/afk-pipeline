# Context: Survivor attribution (issue #304)

## Files and current behavior

- **FACT** — `MutationSurvivor` (`src/mutation-report.ts:45-54`) is `{ id: string; file: string; mutator: string; position: MutationSurvivorPosition }`. `id` is documented (line 47-49) as "the tool's own id, never one minted here: slice 2's decisions file keys accepted survivors by it" — this slice's own comment already anchors the attribution key.
- **FACT** — `MutationStepOutcome` (`src/mutation-report.ts:74-76`) is `{ status: "MUTATION_REPORTED"; survivors: MutationSurvivor[] } | { status: "MUTATION_NOT_RUN"; reason: MutationNotRunReason }`. `MutationNotRunReason` (line 67-71) is `"BOUND_REACHED" | "COMMAND_FAILED" | "REPORT_UNREADABLE" | "REPORT_MALFORMED"`.
- **FACT** — `formatMutationReportLines(report)` (`src/mutation-report.ts:500-528`) is the one formatter both `run-summary.md` and the draft PR body render through; it takes `{ status; reason?; survivors: readonly MutationSurvivor[] }` and returns `string[]`, one bullet per survivor today (line 523-527): `` `- \`${survivor.id}\` ${survivor.file}:${line}:${column} — ${survivor.mutator}` ``. This is the exact function whose per-survivor line the label (`new-in-this-run`/`pre-existing`/`unattributed`/`accepted`) must be appended to, since it is the only call site both consumers share.
- **FACT** — `MUTATION_REPORT_HEADING` (`src/mutation-report.ts:490-491`) is `"## Mutation survivors (reported, never blocking)"`, imported and used identically at `src/ship-gate.ts:528` (PR body assembly, inside `buildPrCreationPlan`) and `src/logger.ts:882` (run-summary render). Both call sites pass `formatMutationReportLines(...)` output straight through — no per-consumer divergence exists to preserve.
- **FACT** — `MutationReportConfig` (`src/mutation-report.ts:31-34`) is `{ command: string; reportPath: string }` — the manifest-parsed shape `runMutationStep` consumes. The issue's `MutationReportDeclaration` type (`src/afk-manifest.ts:52`, unread in full but referenced at lines 84, 190) is the manifest-side counterpart this slice must extend with `baselinePath?` and `decisionsPath?`.
- **FACT** — `AfkManifest.mutationReport` (`src/afk-manifest.ts:84`) is optional and *absent* when undeclared, not an empty object (documented rationale at lines 77-83, tied to GH #303 AC5): "an optional member every existing reader ignores is not a schema break." The same absence discipline governs the two new keys per the issue.
- **FACT** — `normalizeMutationReport(entry, source)` (`src/afk-manifest.ts:187-228`) validates `command` (non-blank) and `reportPath` (non-blank, normalized via `normalizeWaiverPath`, rejects glob via `/[*?[]/`, rejects absolute via `/^(?:[a-zA-Z]:)?\//`, rejects `..` traversal via `.split("/").includes("..")`), then returns `{ command: value.command.trim(), reportPath }` at line 227 — only these two fields. Any key not explicitly read and included in this return object is silently dropped by the JSON-object literal at `parseAfkManifest`'s `return` (`src/afk-manifest.ts:319-326`, `mutationReport` spread at line 325).
- **FACT** — `parseAfkManifest` (`src/afk-manifest.ts:230-327`) requires `version === 1` (line 247-249) and returns a flat object built by explicit field construction (lines 319-326), not a passthrough spread of `input` — so a new key on `mutationReport` must be both read inside `normalizeMutationReport` and included in its returned object, or the manifest rewrite in `trimUnclaimedMigrationPrefixes` (`src/afk-manifest.ts:376-` — spreads `{ ...manifest, migrationPrefixes }` per PRD-1's context notes) will delete it from disk on the next rewrite, exactly the hazard #303's context.md already documents for `mutationReport` itself.
- **FACT** — `normalizeWaiverPath(value)` (`src/afk-manifest.ts:124-126`) is `value.trim().replace(/\\/g, "/").replace(/^(?:\.\/)+/, "")` — the exact normalization the issue says `baselinePath`/`decisionsPath` must reuse ("same one-exact-file normalization as `reportPath`").
- **FACT** — The glob/absolute/traversal refusal logic for `reportPath` (`src/afk-manifest.ts:207-226`) is written inline inside `normalizeMutationReport`, not factored into a reusable "validate one repo-relative path" helper — a new function for `baselinePath`/`decisionsPath` would either duplicate this block or the block would need extracting.
- **FACT** — `readMutationReport(cwd, reportPath)` (`src/mutation-report.ts:190-204`) reads via `readFileSync(join(cwd, reportPath), "utf-8")` inside a `try`, returning `{ status: "UNREADABLE"; detail }` on any read failure — the same pattern a baseline/decisions reader would need, since neither file's absence is ever an error per the issue.
- **FACT** — `parseMutationReport(text)` (`src/mutation-report.ts:120-183`) is pure and total: JSON.parse failure or shape mismatch returns `{ status: "MALFORMED"; detail }` (via `malformed(detail)`, line 99-101), never throws. This is the model the issue's "malformed decisions file degrades to unlabeled survivors" criterion must follow — a parse function that returns a typed result, not a throw, so the caller can classify degradation without try/catch at the call site.
- **FACT** — `RunMutationStepArgs` (`src/mutation-report.ts:321-341`) and `runMutationStep` (`src/mutation-report.ts:357-397`) take `config: MutationReportConfig` (only `command`/`reportPath` today) and derive `files` from `mutationScope`/`buildChangeSummary`; neither reads a baseline or decisions path. Wiring the new config keys into the step (if attribution happens inside `runMutationStep`) versus at the render/formatting boundary (`formatMutationReportLines` callers) is an open design question this context does not resolve (see Unknowns).
- **FACT** — `MutationStepReport` (`src/logger.ts:290-296`) is `{ runSlug: string; status; reason?; survivors: MutationSurvivor[] }` — the persisted/rendered shape neither `run-summary.md`'s writer (`src/logger.ts:877-884`) nor the PR-body assembler (`src/ship-gate.ts:1467, 1478, 1543`) currently carries any baseline or decision label on. `PersistedMutationStep` (`src/run-state.ts:365`, full shape unread beyond the reference) is the run-state-side twin `recordMutationStepOutcome` (`src/run-state.ts:1000-1009`) writes and `readMutationStepOutcome` (`src/logger.ts:325-329`) reads back via `deriveMutationStepOutcome` (`src/logger.ts:306-318`, "last event wins" over `run-events.jsonl` entries of `type: "mutation-step"`, `src/run-events.ts:483`).
- **FACT** — `refuseUndeclaredMutationReport` (`src/preflight.ts:142-160`) refuses the launch only when `--mutation-report` is set and `manifest?.mutationReport` is undefined — it does not inspect `baselinePath`/`decisionsPath` at all, and the issue's settled decisions do not ask it to: both new keys degrade gracefully rather than gating launch.
- **FACT** — No baseline-artifact reader, no decisions-file reader, and no attribution/labeling function (`new-in-this-run`, `pre-existing`, `unattributed`, `accepted`) exists anywhere in `src/` (confirmed via targeted grep for `baselinePath`, `decisionsPath`, `pre-existing`, `unattributed`, `new-in-this-run`, `accepted` — no matches outside this issue body and ADR 0071).
- **FACT** — ADR 0071 (`docs/adr/0071-report-only-mutation-survivor-step.md`) already specifies the decisions-file schema in its "Decisions file schema" section: "Each entry carries the mutant identity, the consequence if the mutant were real, the containment that makes it acceptable, a verdict of KILL or ACCEPT, and one line of reasoning," with "The file's version regime matches the manifest's — `version: 1`, refused when absent or different, validated by the same `parseAfkManifest` discipline that governs `afk.json`." **INFERENCE** — "validated by the same `parseAfkManifest` discipline" reads as "the same fail-closed, name-the-offending-member style," not literally routed through `parseAfkManifest` itself, since the decisions file is a separate committed artifact at `decisionsPath`, not a member nested inside `afk.json`; no code confirms which function will parse it.
- **FACT** — ADR 0071 states outcomes are "persisted in run state with the run's own run id as provenance" and that this slice's parent settled decision (this issue's body) requires "report assembly stays a pure function over the parsed survivor list, the optional baseline artifact, and the optional decisions file" — i.e., attribution is explicitly scoped as a pure function over three already-available inputs, not a step that re-reads git or re-runs anything.

## Data and integration

- **FACT** — The two new config keys land inside the same `mutationReport` object member 303 introduced on `AfkManifest` (`src/afk-manifest.ts:84`), per the issue's "Config surface" section — not a new top-level manifest member, not a CLI flag (issue: "Do not resolve either path from a CLI flag or from a `package.json` script convention"), and not routed through `cli-options.ts`'s existing `mutationReport?: boolean` flag (`src/cli-options.ts:119`, `258`, `298`), which is an unrelated on/off toggle for `--mutation-report`, distinct from the manifest's `mutationReport` config object.
- **FACT** — Both new keys must be **returned** by `parseAfkManifest`, per the issue: "The ship gate rewrites `afk.json` from the parsed object, so a key the parser drops is deleted from the reviewed feature branch — the same hazard #303 records for `mutationReport` itself." This is the same hazard already documented above (`normalizeMutationReport`'s narrow return object, `parseAfkManifest`'s explicit-field return).
- **FACT** — `afk.json` stays at `version: 1` per the issue, consistent with ADR 0071's "The file's version regime matches the manifest's" line about the *decisions file*, and with `parseAfkManifest`'s existing flat check (`src/afk-manifest.ts:247-249`).
- **FACT** — The three inputs the pure attribution function takes, per the issue's "settled decisions": "the parsed survivor list, the optional baseline artifact, and the optional decisions file." The survivor list's shape is `MutationSurvivor[]` (above). Neither the baseline artifact's shape ("the tool's incremental file" — StrykerJS's own incremental-run cache, per the issue) nor the decisions file's shape (ADR 0071's schema: mutant identity, consequence, containment, KILL/ACCEPT, one-line reasoning) has a parser or TypeScript interface anywhere in `src/` yet.
- **FACT** — This slice's own acceptance criteria explicitly forbid gate/verdict/PR-open participation: "No gate, verdict, or PR-open decision keys on any survivor label" — consistent with `formatMutationReportLines`'s and `MUTATION_REPORT_HEADING`'s existing "reported, never blocking" framing and ADR 0063's "measured, never gates" posture, which this slice's labels must also follow.
- **FACT** — `runShipGate` (`src/ship-gate.ts:651-`) already threads `mutationReport?: MutationReportConfig` (line 654) through to `runMutationStep` (lines 1009-1023) inside the merged review worktree (`cwd`) — the same `cwd` a baseline-artifact or decisions-file reader would read from, since both are "committed" artifacts in the consuming repo per the issue (i.e., present in the same worktree the mutation command already runs in).

- **UNKNOWN** — What identity field on a `MutationSurvivor` a baseline lookup and a decisions-file lookup key on — the issue and ADR 0071 both say "mutant identity" / "the tool's own id" without specifying whether that is `MutationSurvivor.id` alone, or `id` plus `file` (since Stryker mutant ids are commonly scoped per-file and could collide across files without the path).
- **UNKNOWN** — Whether the "malformed decisions file" degradation path needs a new `MutationNotRunReason`-shaped enum for labeling specifically, or whether it only affects the survivor labels (leaving them all `unattributed`/unlabeled for decisions) while the step's own `MUTATION_REPORTED`/`MUTATION_NOT_RUN` status is untouched — the issue's own acceptance criteria say a malformed decisions file "never classifies the step as `MUTATION_NOT_RUN`," which rules out reusing `MutationNotRunReason` for this case, but does not say what vocabulary (if any) marks the degradation in `run-summary.md`.
- **UNKNOWN** — Whether `baselinePath`/`decisionsPath` validation needs a shared helper factored out of `normalizeMutationReport`'s inline glob/absolute/traversal checks (`src/afk-manifest.ts:207-226`), or whether each new key duplicates that logic inline — no existing precedent for a three-times-repeated path-validation block exists yet in this file to say which the codebase prefers.
