# Context: Mutation report step (issue #303)

## Files and current behavior

- **FACT** — The ship gate is orchestrated by `runShipGate(args: RunShipGateArgs): Promise<ShipGateResult>` in `src/ship-gate.ts:651`. It runs pre-ship sanity, then dispatches the two guardian reviews, then decides the PR-open outcome.
- **FACT** — Guardian dispatch and rejoin: when `options.serialReviews` is false (the concurrent default), both guardians are launched together via `await Promise.allSettled([...])` at `src/ship-gate.ts:935-940`. Each element is either a cached result (`Promise.resolve(cached)`) or `runGuardianReview(kind)` (defined at `src/ship-gate.ts:758`).
- **FACT** — Guardian-rejection handling today: `Promise.allSettled` never throws itself; a settled `"rejected"` entry is re-thrown synchronously by the caller at `src/ship-gate.ts:941-944` (`if (architectSettled.status === "rejected") throw architectSettled.reason;` and the PM equivalent). This is the "guardian-rejection exit" the issue's F-08 finding is about — today it has no await on anything else and no bound, because there is no mutation step yet.
- **FACT** — There is no `mutationRun` seam, mutation step, or `--mutation-report` flag anywhere in `src/` yet (confirmed via targeted grep of `ship-gate.ts` and repo-wide symbol search during exploration — no matches).
- **FACT** — `runGuardianReview` (`src/ship-gate.ts:758-`) invokes the architect/PM agents and computes `ReviewRunResult`; its outcome feeds `journal.setReviewOutcomes(architectResult, pmResult)` at `src/ship-gate.ts:998`, then persisted guardian round records (`guardianRecord`, `src/ship-gate.ts:1000-1029`) and `completedRound` (`src/ship-gate.ts:1030-1038`).
- **FACT** — The PR-open decision is downstream of both guardian outcomes: a `blocked(...)` return happens when `!prPlan.open` (per exploration, `src/ship-gate.ts` ~1377-1386). Any new step's outcome must not participate in this decision, per the issue's requirement.
- **FACT** — `afk.json` is parsed by `parseAfkManifest(value, source = "afk.json"): AfkManifest` in `src/afk-manifest.ts:143-232`. Current `AfkManifest` interface (`src/afk-manifest.ts:39-52`): `{ version: 1; selectedSlices: string[]; migrationPrefixes: string[]; protectedIssues: ProtectedIssue[]; protectedChangeWaivers?: ProtectedChangeWaiver[] }`. `version !== 1` throws `` `${source} must declare version 1` `` at line 160-162 — there is no version-bump mechanism for `afk.json` itself; it is a flat "always 1" check, distinct from `RUN_STATE_VERSION`.
- **FACT** — Current repo's own `afk.json` for this PRD (`.kiro/specs/mutation-survivor-report/afk.json`) has no `mutationReport` member: `{"version":1,"selectedSlices":["01","02"],"migrationPrefixes":[],"protectedIssues":[{"number":302,"state":"OPEN"}]}`.
- **FACT** — `normalizeWaiverPath(value: string): string` (`src/afk-manifest.ts:91-93`) is `value.trim().replace(/\\/g, "/").replace(/^(?:\.\/)+/, "")` — the exact normalization the issue says `reportPath` must reuse.
- **FACT** — Glob rejection precedent: `normalizeProtectedChangeWaiver` rejects a path matching `/[*?[]/` with a message calling it "a glob" (`src/afk-manifest.ts:127-134`). No existing check rejects `..` traversal or absolute paths anywhere in `afk-manifest.ts` — this would be new logic for `reportPath`.
- **FACT** — The manifest-rewrite-must-carry-forward-unknown-members risk is real and already load-bearing: `trimUnclaimedMigrationPrefixes(prdDir, claimedPrefixes)` (`src/afk-manifest.ts:281-309`) calls `parseAfkManifest` (line 289) and then spreads `{ ...manifest, migrationPrefixes }` (line 306) before `writeFileSync`. Any member `parseAfkManifest` does not return (i.e., not included in the object built at lines 225-231) is silently dropped by this rewrite.
- **FACT** — `canonicalSliceNumber` (`src/afk-manifest.ts:240-`), `assertWithinManifestScope<T>(...)` (`src/afk-manifest.ts:252-266`), and `loadAfkManifest(prdDir)` (`src/afk-manifest.ts:269-273`) are the other exported manifest helpers.
- **FACT** — The manifest fail-closed block in the orchestrator is at `src/orchestrator.ts:8497-8508`, inside the top-level `try` of the run, guarded by `if (config.manifest && requestedSliceNumbers)`, calling `assertWithinManifestScope({...})` and throwing via that helper on conflict. This runs before `updateRunState` (line 8509) and before any worktree/dispatch — the place the issue says the mutation-config refusal belongs, "beside" this block.
- **FACT** — `src/preflight.ts` defines `PreflightCheck` (line 107), `PreflightFinding` (line 113: `{ check, severity: "refuse" | "report", message, pids? }`), and `PreflightReport` (line 127: `{ findings: PreflightFinding[]; ... }`). `runLaunchPreflight` builds `findings` (declared line 266) and computes `refuse` at lines 449-451: `` const refuse = request.reportOnly !== true && findings.some((finding) => finding.severity === "refuse"); `` — i.e. `--preflight-report-only` (`reportOnly: true`) always suppresses a `PreflightFinding`-based refusal. This is exactly why the issue insists the mutation-config check must be a plain `throw`, never a `PreflightFinding` — going through `PreflightFinding` would make it bypassable by that flag.
- **FACT** — `formatPreflightRefusal(report)` (`src/preflight.ts:643-`) is the operator-facing renderer for finding-based refusals; it explicitly tells the operator to "pass --preflight-report-only to launch anyway" (line 651) — confirming findings are meant to be overridable, unlike the new manifest-config throw.
- **FACT** — Change-summary builder: `buildChangeSummary(cwd, fromRef, toRef): ChangeSummary` (`src/change-summary.ts:178-197`), returning `{ version: 1, fromRef, toRef, commits: ChangeSummaryCommit[], files: ChangeSummaryFile[], totals: {...} }`. `ChangeSummaryFile` (`src/change-summary.ts:36-43`) is `{ path, status, insertions: number|null, deletions: number|null }`. This is the "existing change-summary builder" the issue says must be filtered to derive mutation-eligible file scope.
- **FACT** — `buildFinalChangeSummary` (`src/change-summary.ts:291-`) is the baseline→final variant, calling `buildChangeSummary` per overall diff (line 339) and per post-approval stage (line 346: `byStage[stage.stageId] = buildChangeSummary(...)`) — precedent for attributing a diff to a specific run stage, similar to how the mutation step would scope to "the files the run changed."
- **FACT** — `runBoundedCommand(command, args, options: BoundedCommandOptions): Promise<CommandExecutionResult>` (`src/command-runtime.ts:60-`) is the existing bounded-process seam: it takes `wallClockTimeoutMs?`, `signal?: AbortSignal`, spawns via `node:child_process.spawn`, calls `registerWorktreeProcess(options.cwd, proc)` immediately after spawn (line 76), and returns `CommandOutcome` = `"EXITED" | "SPAWN_ERROR" | "CANCELLED" | "INACTIVITY_TIMEOUT" | "WALL_CLOCK_TIMEOUT"` (lines 25-30). This is the strongest existing candidate for the "mutationRun seam" the issue names, since it already has process registration, a wall-clock bound, and abort-signal cancellation built in.
- **FACT** — `registerWorktreeProcess(cwd, proc)` (`src/worktree-processes.ts:60-66`) records a spawned process against its `cwd` in an in-memory `Set<Entry>` (line 47); `quiesceWorktree(...)` (`src/worktree-processes.ts:138-`) later waits for / terminates everything registered against a worktree, returning `{ observed, terminated, survivors, verified }`. This is the "existing quiesce path" ADR 0020/0035 and the issue reference.
- **FACT** — `src/kill-tree.ts` exports `terminatePidTree` and `terminateProcessTree`, imported by both `worktree-processes.ts` (lines 6-9) and `command-runtime.ts` (lines 11-14) — the underlying kill mechanism ADR 0020 (tree-first, verified) governs.
- **FACT** — No generic named `withTimeout`/`boundedAwait` helper exists in `src/` (grep across the repo found none). The closest analogous pattern is the per-invocation wall-clock ceiling in `src/invocation-runtime.ts`, implemented inline with `setTimeout`/`ceilingTimer` state (`src/invocation-runtime.ts:218-352`), not a reusable utility. **INFERENCE** — bounding every exit that awaits the mutation step (per the issue's settled decision) will need either a new small bounded-await helper or reuse of `runBoundedCommand`'s existing `wallClockTimeoutMs`/`signal` plumbing rather than borrowing a nonexistent generic timeout utility.
- **FACT** — `src/run-state.ts:67` declares `export const RUN_STATE_VERSION = 6;`, with the persisted state's `version` field typed `3 | 4 | 5 | 6` (`src/run-state.ts:254`) — this is the schema-version regime ARCHITECTURE.md's "new persisted fact extends run-state's schema with a version bump" rule governs, and it is a different version number/regime than `afk.json`'s flat `version: 1`. **INFERENCE** — the ADR this slice must write (per the issue) needs to state explicitly that `afk.json` does not participate in `RUN_STATE_VERSION`'s bump discipline, since a reader of ARCHITECTURE.md's generic rule could otherwise assume it does.
- **FACT** — `run-summary.md` is written by the `Logger` class: `writeFileSync(join(...), "run-summary.md", summary)` at `src/logger.ts:875` and `:879` (two write sites). A bounded-line-length comment sits at `src/logger.ts:1068`. `src/orchestrator.ts:669` documents the path as `.afk/logs/<slug>/run-summary.md`.
- **FACT** — The draft PR body is not a separate template file; it is assembled inside `src/ship-gate.ts` — `buildPrCreationPlan` (line 336 per exploration) builds the plan and the actual `gh pr` invocation happens around lines 1421-1429. Both `MUTATION_REPORTED`/`MUTATION_NOT_RUN` text must be added at this ship-gate PR-body assembly site as well as in the `Logger`'s run-summary writer.
- **FACT** — `quality-stage-attempt` in `src/run-events.ts:440-461` is the closest existing precedent for a "measured, non-gating" step outcome event: it records `ghIssue`, `sliceNumber`, timings (`startedAt`, `endedAt`, `durationMs`), `outcome: string` (a stage-owned vocabulary, not a shared enum), and is explicitly documented (lines 425-429) as "Measurement, never a gate (ADR 0063): nothing thresholds, alerts on, or branches on any number here." **INFERENCE** — the mutation outcome's `MUTATION_REPORTED`/`MUTATION_NOT_RUN` recording likely follows this same non-gating, run-events-style precedent, though it is a run-scoped fact (one per run) rather than a per-slice/per-attempt one like `quality-stage-attempt`.
- **UNKNOWN** — No existing top-level "run-ID" field name was located on the persisted run-state object during this exploration (searches for `runId`/`loggerSlug`/`runSlug` inside `run-state.ts` only matched function parameters, not a stored field). It is unresolved what exact field/shape "run-ID provenance" (per the issue's acceptance criteria) should reuse or add on the persisted state.

## Data and integration

- **FACT** — The `mutationReport` config shape declared in the issue is `{ command: string; reportPath: string }`, added as an optional member on `AfkManifest`, parsed and returned by `parseAfkManifest`, and required to survive `trimUnclaimedMigrationPrefixes`'s spread-based rewrite (`src/afk-manifest.ts:306`).
- **FACT** — The external report format AFK must parse is the "mutation-testing-elements" JSON schema (as emitted by StrykerJS and peers) — no existing parser for this schema exists anywhere in `src/` (confirmed via exploration).
- **FACT** — The mutation step's file scope is derived from `buildChangeSummary`'s `ChangeSummaryFile[]` (`src/change-summary.ts:36-43`, `path`/`status`/`insertions`/`deletions`), filtered to "mutation-eligible source files" per the issue — no existing filter/allowlist for "mutation-eligible" file types exists in the codebase yet.
- **FACT** — The mutation command runs "on the merged feature branch" / "the ship gate's merged review worktree" per the issue — this is the same `reviewDir` already passed into `runShipGate` (`src/ship-gate.ts:656`, destructured from `RunShipGateArgs`), i.e. no new worktree needs to be created for this step.
- **FACT** — ADR precedent for report-only/non-blocking measurement steps: ADR 0063 ("A wall-clock budget cannot fail a gate") and ADR 0046 ("Bounds are reported, stage durations are recorded, and nothing alerted") both govern the "measured, never gates" posture this issue's mutation step must also follow. ADR 0020 ("Windows process-tree termination") and ADR 0035 ("Worktree teardown quiesces processes") govern the termination/quiesce requirements this issue cites directly. ADR 0038 ("The generator's verification command is its own decision") is the precedent the issue's "Rejected — companion CLI flags" section explicitly analogizes to and distinguishes from (a flag may later *narrow* a declared value, as `--test-command` does under ADR 0038, but that is out of scope here). ADR 0034 ("The afk.json manifest and pipeline-owned migration claims") is the ADR that already establishes `afk.json` as the cross-repository contract this slice's `mutationReport` member extends.
- **FACT** — Per the issue, the next unclaimed ADR number (checked across every ref via `git log --all --diff-filter=A --name-only --pretty=format: -- 'docs/adr/*' | sort -u`) was **0071** as of the issue's 2026-09-14 decision. **INFERENCE** — this number should be re-verified at implementation time rather than trusted as still current, since the issue itself warns that `docs/adr/` numbering has collided across branches before (#249) and other slices/branches may have claimed 0071 since 2026-09-14.
