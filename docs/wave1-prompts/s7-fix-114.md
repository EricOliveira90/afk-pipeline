The defect, observed stopping a live run on Windows: CTRL_C_EVENT sent to
the orchestrator's node PID did nothing; CTRL_C_EVENT to the parent
cmd.exe console did nothing; only CTRL_BREAK_EVENT stopped it — and that
exit bypassed the abort bookkeeping entirely: no stop line in run.log, and
the in-flight slice got NO run-state entry (which sets up the #113
destruction on the next `--only-failed`).

Designed behavior (ADR 0003, `docs/adr/0003-cancellation-via-abortsignal.md`):
SIGINT triggers the AbortController in the entry points (`src/afk.ts`,
`src/afk-claude.ts`, `src/afk-codex.ts`), in-flight agents get SIGTERM,
unstarted/in-flight slices are marked CANCELLED in state. ADR 0020 covers
Windows process-tree termination.

Two things to fix, in this order:

1. Exit-path integrity first: whatever signal ends the process through the
   abort path must write the cancellation record and mark in-flight slices
   CANCELLED in run state BEFORE exit. This half matters more — a stop
   that records itself is recoverable even if it takes the wrong signal.
2. Signal delivery: make one documented signal reach the abort path from a
   normal Windows console launch. Investigate whether the handler misses
   CTRL_C_EVENT (Node signal semantics on Windows) or the cmd.exe wrapper
   swallows it; document the finding in the PR even if the fix is partial.
