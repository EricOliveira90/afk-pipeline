# Primary-source check: hooks research

Checked 2026-08-29 against current first-party documentation and source repositories only.

## Verdicts

| Claim | Verdict | Source check and required correction |
|---|---|---|
| Claude Code `PreToolUse` supports exit-2 deny and `permissionDecision: "ask"` | **Supported, with caveats** | A command hook exiting 2 blocks the tool call and sends `stderr` to Claude. Structured `permissionDecision` supports `allow`, `deny`, and `ask`; `ask` prompts the user. The docs also say permission-system deny and ask rules are still evaluated after hook output. The research's stronger wording about an ask being labelled by source and immune to an “auto-approval classifier” was not established in the checked hook reference and should be removed or separately sourced. Other nonzero exits and timeouts are non-blocking errors, so Claude hooks are fail-open except for explicit exit 2 or a structured deny. |
| Claude settings scope, precedence, and project-hook trust | **Partly supported; trust risk understated** | Settings precedence is managed > command line > local project > shared project > user. Hook entries can exist in managed, user, project, local, plugin, skill, and agent settings. Shared project settings live in `.claude/settings.json`, are intended for source control, and can be edited directly; Claude can also be asked to configure hooks. Settings changes are detected during a session. Therefore project hook config and project-resident hook scripts are agent-editable files unless an external permission boundary or higher-precedence managed policy protects them. `ConfigChange` can block settings changes during a session, but it does not make arbitrary project hook scripts tamper-proof. |
| Cursor `failClosed`, event coverage, and config precedence | **Supported; project trust needs an explicit warning** | `failClosed` defaults to `false`; hook failure, timeout, or invalid output blocks only when it is `true`. Cursor documents generic `preToolUse`/`postToolUse`, shell, MCP, file-read/edit, subagent, prompt, stop, compaction, and session events, with stated cloud-agent limitations. All matching hooks run; conflict precedence is Enterprise > Team > Project > User. Project hooks are loaded from `.cursor/hooks.json` in a trusted workspace, are designed for version control, and reload when saved. This means an agent able to write the repository can edit project hook config or scripts. The checked docs describe no Gemini-style fingerprint prompt for each changed hook. Enterprise or team hooks are the defensible trust anchor, not project hooks alone. |
| Gemini CLI fingerprints hooks and defines project/user precedence | **Supported, but fingerprinting is narrower than tamper-proofing** | Gemini documents hook fingerprinting: changes to a hook's `name` or `command` make it new/untrusted and trigger a warning. It also documents precedence as project > user > system > extension. Trusted Folders can prevent project settings and `.env` loading in untrusted folders. However, the hook docs describe the fingerprint in terms of name and command, not the contents of a script invoked by an unchanged command. The research should not imply that fingerprinting secures all project hook code against in-worktree modification. Project precedence also means a project config can outrank user config; organization-grade policy needs a stronger boundary than a user file. |
| Codex CLI has no general hook system and relies only on sandbox/approvals/rules | **Contradicted by current official docs** | Codex now documents a general lifecycle-hook system, enabled by default, with `SessionStart`, `Stop`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, and other events. It supports exit-2 blocking, structured decisions, project/user/managed hooks, project trust hashes, and managed-hook precedence. `PreToolUse` covers shell commands, `apply_patch`, MCP calls, and most local function tools, but hosted tools such as web search and specialized paths can bypass it; `ask` is parsed but not enforced. Sandbox, approvals, and exec rules therefore remain the stronger parity floor, but “Codex has no hook system” and “there is no observe/mutate channel” must be deleted. |
| A portable protocol exists across Claude, Cursor, and Gemini | **Common substrate supported; drop-in portability overstated** | All three use JSON over standard input/output and reserve exit 2 for blocking. Cursor explicitly documents Claude Code compatibility and can load supported Claude hook settings; Gemini exposes `CLAUDE_PROJECT_DIR` as a compatibility alias. That supports a portable **hook executable** on a limited common subset. It does not support the broad claim that hooks “written once” port unchanged: event names, config locations, matchers, output fields, supported decisions, and tool coverage differ. Cursor maps only supported Claude events and warns that behavior differs; Gemini uses its own event/config schema. Historical priority (“Claude Code defined it”) is also not proven by these product references. Phrase this as an emerging compatible transport convention requiring provider adapters, not a de facto portable hook standard. Current Codex docs now add a fourth Claude-shaped implementation, again with incomplete coverage. |
| Liquibase applies governance checks to AI-generated SQL | **Supported as a product claim; marketing and mapping caveats required** | Liquibase says policy checks inspect changelogs/changesets before deployment, can halt a deployment on violations, and apply the same checks regardless of whether SQL was written by a human or generated by AI. Its official AI-SQL article explicitly recommends policy checks as guardrails before deployment. These are vendor product and marketing claims, not independent evidence of effectiveness or adoption. Liquibase supports the general “deterministic pre-deploy policy” analogy; it does not establish AFK's reserved-prefix design, tool-call hook enforcement, or the claim that this is an industry-standard agent-hook pattern. |

## Bottom line

Keep the research's hook-archetype synthesis, but revise three foundations before using it for AFK planning:

1. Treat project hook files as mutable workload inputs, not a policy root.
2. Describe portability as provider-adapted reuse of a common JSON/exit-code subset.
3. Reassess the AFK backend comparison now that Codex exposes hooks, while retaining sandbox and orchestrator gates as the cross-provider enforcement floor.
